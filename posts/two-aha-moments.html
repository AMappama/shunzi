两个 aha moment 之后，一切才开始

08.13.26 · Shunzi

项目：MedRWA Console —— 医疗应收（医保/商保）收益权 RWA 运营台 Demo。

项目能跑通之后，我还缺什么

MedRWA 最初的目标很直接：做一个能演示的全栈 Demo。资产登记、审核、映射、认购、回款、对账、凭证、审计——链路跑通，页面能点，接口能通，按很多教程的标准，这已经算完成了。

我也确实处在一种很舒服的状态里：任务来了，让 AI 写前端；缺规则，让 AI 补后端；Docker 出问题，再切过去排查。每天都在推进，每天都在交付。

但在读两篇帖子之前，手动跑流程时已经撞上过两次不对劲。它们修掉了，却没有变成可复用的方法——经验停在那一次排查里，下次还要重新来过。

直到我在 Knowledge Bank 看到两篇帖子。它们没有教我新的 Prompt，也没有推荐新的工具。它们各自给了一个 aha moment：是我改变思维方式的重要转折点，也是之后岗位裁剪、多 Agent 分工、SOP 和 Skill、Issue 留痕、提问方式转变这些动作的开端。

读两篇帖子之前：两件事已经让我不安

这两件事都发生在主链路已经能跑、我还在「交付状态」里的时候。当时我做了该做的修补，却没有把它们接进一套能沉淀、能复用的结构里。

那笔错误的账

系统已经能跑完整条链路。我登记了一笔回款：金额与资产完全一致，只是回款方不一样——资产属于医保，钱却来自商保。

系统给出的结果是：匹配成功。没有报错，没有崩溃，页面甚至给出了令人安心的成功提示。

能发现这个漏洞，医疗行业里 来源核对 的习惯帮了大忙。我补上第二重校验：医保资产必须对应医保对手方，不一致则标记 COUNTERPARTY_MISMATCH，禁止错误放行。

问题当时已经浮现，但我还没有一套语言把它说清楚：程序跑对了，账却可能错了；谁来定义什么叫「对」？

一分钱尾差

对账修完之后，复盘时又碰到一个更小的问题：回款按持仓比例分配，除不尽会产生一分钱尾差。常见工程手法是 最后一笔吃尾差——总金额能平，代码也没错。

我继续追问：为什么由最后一笔承担？合同有没有写？规则会不会长期偏向某一类投资人？没有足够证据回答这些问题。

我没有为了显示行动力立刻改代码，也没有因为只有一分钱就忽略它。问题被标记为 ACCEPTED_RISK，写明产品化前必须补充合同与法务约定。

连决定不修，也需要有人留下名字。 但当时这只是一条 Issue，还没有接上「判断 → 验证 → 沉淀」的迭代闭环。

第一个 aha：最危险的不是不用 AI，而是只会用 AI

来源：最危险的不是不用 AI，而是只会用 AI

文章里区分了两种使用 AI 的方式。一种我称之为 交付状态：任务 → AI 帮忙 → 交出去 → 等下一轮。AI 让你在同一条旧流水线上跑得更快，但任务结束后，可能什么都没有留下。

另一种是 迭代状态：输入从哪来，判断怎么做，行动怎么执行，结果如何验证，错误怎么处理，经验如何沉淀，下一轮怎么因此变得更好。

那一瞬间我意识到：MedRWA 已经能演示了，串账和一分钱我都处理过，但我还在交付状态里。代码是 AI 写的，流程是我跑通的，可这些东西大多躺在仓库和聊天记录里。下一次遇到类似问题，还是要重新输入、重新处理、重新输出。AI 帮我节省了时间，这项工作本身 却没有因此变得更聪明。

aha 之后我做的第一件事：加闭环。

我把过程里真正起作用的东西固化下来：

  • 六部分 Prompt 骨架（目标、上下文、业务规则、范围、规范、验收标准）；
  • 四份 SOP（需求拆解、AI 产物验证、全栈联调、Docker 排障）；
  • 项目级 Skill（一键启动 Demo、结构化记录 Issue）；
  • 39 个问题的分级归档——从 npm 是做什么的 到 旧流水补回单号会不会引发投诉。

这些看起来没有增加菜单数量，却在回答迭代闭环里的几个硬问题：结果怎么验证？错误怎么处理？经验怎么沉淀？

我也开始改变向 Agent 提问的方式。除了 能不能生成，还会问：

  • 这个规则保护了谁？可能误伤谁？
  • 哪一部分是事实，哪一部分只是推测？
  • 如果决定暂时不修，风险由谁接受？

有价值的问题不一定带来更多代码。它也可能让一个功能延期，让一项风险被记录，或者让团队承认目前还不知道答案。

串账和一分钱若只停在「当时修掉了」，就还是交付物；接上 SOP、Skill 和 Issue 规范之后，它们才变成下一轮可以调用的经验。这是第一个 aha 在项目里的落地方式。

第二个 aha：像素已死，系统永生

来源：像素已死，系统永生：与 Cursor 设计负责人 Ryo 聊 Builder 时代的到来

这篇给我留下的冲击，比几条具体观点更深。

Ryo 是设计师，谈的东西却处处像软件架构师在想的：概念怎么分层、关系怎么连、系统怎么在运行中反馈。我们习惯把设计师理解成画图、做视觉、调审美的工种；Ryo 却给人一种 两种职业融在一起 的感觉。若设计思维和架构思维之间没有共性，怎会 殊途同归？

他谈到世界上很多事彼此有共性——不同领域背后往往是相近的结构。我在他的推演和表达里慢慢接受了这一点，也很认可：概念、边界、反馈环路，并不只属于某一张架构图或某一个画布，它们可以跨工种、跨工具出现。设计师跳进代码里做原型，架构师用状态机和契约钉住规则，表面路径不同，底层却在处理同类问题。

带着这种感受回头看 MedRWA：我此前堆起来的，很多是 能演示的界面；那些不容易被替代的东西——谁有权、钱该归谁、过程能否追溯、规则变化如何留历史——还没有被当成骨架先固定下来。

第二个 aha 之后，我先搭骨架。

框架会换，热门技术会换，今天先进的 AI 能力明天可能被另一种实现替代。钱从哪里来、对象是否一致、谁有权确认、过程能否追溯——这些不会因为 React 升级就消失。

所以 MedRWA 优先留下的是：

  • 资产状态机与角色边界；
  • 对账时金额 + 资金对象的双重校验；
  • 凭证须人工确认、关键操作写审计；
  • OpenAPI 契约、Flyway 迁移、按角色裁剪的数据视图。

真链、Redis、以及 为了显得像 AI 产品 而加大模型功能，都被刻意往后放。暂时还没有证据证明它们在这个 Demo 里不可缺少。

我希望系统里每一块都能从现实生活找到原型：医院按批次管理应收，回款必须找到正确对象，入账需要有人确认，规则变化需要保留历史。实现可以更换，这些关系仍然存在。

前端我在做 减法：每个角色登录后，菜单只保留自己链路里必要的入口；看板只展示当前岗位最关心的指标；页面用一句 page-hint 锚定上下文，少堆说明框和引导动画。

组织效率不一定来自每个人做得更多。很多时候，它来自每个人看到的更少，但更清楚下一步该做什么，也更容易判断 自己这一段有没有负责到底。

完成是一层层增加的信息

做项目时，我们很容易把结果压缩成两个状态：成功或者失败，完成或者未完成。

真实工程更像不断展开的一组条件：

  • 页面能否操作；
  • 接口能否返回；
  • 金额能否算平；
  • 资金对象是否一致；
  • 新规则会不会误伤历史数据；
  • 出现例外时由谁判断；
  • 最终结果由谁承担责任。

每多问一层，信息就多一点，原本清晰的答案也可能重新变得模糊。

比如银行回单号——这是在 aha 之后、提问方式转变时遇到的典型例子。把它设为必填并不复杂：前端限制输入，后端增加校验，对账前再次检查。可当规则面对已经存在的旧流水时，问题就变了：是直接禁止对账，还是允许补录？是否需要过渡期？有没有人工豁免？

此时继续讨论使用什么注解、修改哪个 Service，已经无法让答案更完整。技术实现回答了 规则怎样执行，规则落到真实用户身上会发生什么 仍悬而未决。

这是第一个 aha 在日常开发里的延续：用提问防止答案过早封闭。

岗位小闭环：业务角色，也是 Agent 角色

业务里每个角色需要 各管一段、负责到底，我和 Agent 的协作也按同一套逻辑重组。

业务三角色：

岗位负责完成的链路不进入的环节
医院运营建资产 → 登记回款不处理平台对账
平台运营审核 → 映射 → 对账 → 生成凭证草稿不替投资人确认入账
投资财务认购 → 查看回款 → 确认凭证不创建医院资产

前端根据角色裁剪菜单和路由，看板只展示当前岗位最重要的指标；后端再校验一次权限，避免仅靠隐藏按钮制造安全感。

工程五角色：

人类：确定业务目标，决定风险，完成最终审批
主 Agent：拆解、契约、集成、验收
领域 Agent：前端 / 后端 / 数据库 / 平台 —— 在各自边界内实现并提交证据

当改动跨越前后端时，先对齐 OpenAPI；涉及数据结构时，先明确 Schema 和迁移；提交结果时，不以 已经完成 作为证据，而要带上实际改动、测试输出、风险和回滚方式。

如果一个 Agent 包办所有事情，短期很快，长期却在边界处丢失信息。多个 Agent 各自完成一个小闭环，减少了互相覆盖、重复理解和集成返工。

协作由此开始具备组织结构：概念边界 落在业务角色上；迭代闭环 落在 Agent 分工与验收证据上。这是两个 aha 在工程协作上的汇合。

让系统多活一层

回头看，两个 aha moment 其实在处理同一件事。

第二个 aha 指向：先固定概念和反馈结构，系统才能长期生长。 第一个 aha 指向：判断、验证、沉淀必须成环，工作才不会每次从零开始。

岗位闭环回答 谁负责把事情做到结束。 有价值的提问回答 结束之前还缺少什么信息。

前者防止责任扩散，后者防止答案过早封闭。它们共同保护的是系统面对真实世界时仍能继续解释、继续修正的能力。

代码可以由 AI 大量生成，任务也可以由多个 Agent 并行完成。谁负责到底、问题由谁提出、风险由谁接受，这些不会自动出现在补全结果里。

下一次系统亮起绿色的成功提示时，也许不必立刻怀疑它，更不必立刻相信它。

只需要再多问一句：

现在这个成功，包含了谁所知道的现实？

写在最后

两篇帖子没有直接告诉我该做什么功能。它们各自给了一个方向：

  • 第一篇：最危险的不是不用 AI，而是只会用 AI —— 搭能沉淀经验的闭环，别停在交付状态。
  • 第二篇：像素已死，系统永生 —— 先固定 runtime 里真正长寿的概念，再谈界面。

MedRWA 是我在这两个方向上做的一次实验。代码接近 100% 由 AI 生成；我负责的是各段责任是否清晰、什么规则必须留下、什么问题值得问、以及什么风险必须留下名字。仓库里的 SOP、Issue、多 Agent 文档和那份 39 个问题的统计，是 aha 之后主动留下的痕迹。

项目地址：MedRWA Console。docker compose up --build 可以直接跑；docs/ 目录下有完整案例文档、SOP 和 issue 记录。
