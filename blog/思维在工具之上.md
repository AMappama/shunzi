# 思维逻辑在工具之上

> 项目：[industry-select-product](https://github.com/AMappama/industry-select-product) —— **选销易**，工业零部件选型。微信小程序给工程师选型号、出图纸和订货单；接口在 NestJS 里；运营后台用 Vue。

这一天更像一次逆向实验。桌上是一款已经做完的产品，我想从它被做成的样子里，摸到制作时怎么想。怎么把页面抄像，我没有打算沉淀成一套做法。

**工具之上是方法，方法之上是习惯，习惯之上是思维逻辑。** 思维逻辑一旦站住，习惯会自己长出来；习惯稳住之后，方法才会在大量坚持里自己现身。

我把「思维逻辑」收窄成四问，否则这个词会漂：工程师来干什么；这项作业在离开屏幕之后算不算做完；决策在哪一分叉（进目录查，还是进工况算）；哪些结果必须在成交当下钉死。小程序是什么、SaaS 能不能塞进微信、包体积卡哪条线，我也问了，那是承载层的预研，回答的是「放不放得进这个容器」，回答不了上面四问。

实际顺序也没有标题听起来那么干净。我先问了容器，再拆屏，店的比喻还能走很远，公式那一屏作业才露面。四层框架是事后用来安放这一天的，开工前并没有一张已经画好的施工图。

上一件让我把全栈跑通的，是 [MedRWA Console](https://github.com/AMappama/med-rwa-demo)。那时我从选栈和页面能点开始。链路跑完，对账按金额匹配会放行一笔来源不对的回款。程序在交付，我对「什么叫对」说得太少。选销易这一天，我想先盯作业本身。对照的是我自己的两次，能核对的也只有我自己留下的记录。

---

## 谁在选，选完要带走什么

打开首页时，轮播、分类、加购、收藏都在，货架上躺的是工业零件。衣服出穿搭，化妆品出妆容，零件出配套，这个形式我见过，所以新东西好像不多。

拆屏用汉语，每屏只写：人来这里要做完哪一项作业，什么进、什么出，后台得备什么，这一步搁在整条链的哪一截。目录、详情、加购都还很像店。若到此收笔，我会交出一份电商拆解。

作业在货架下面：翻样本、对参数、校核工况、定型号、要图纸、开订货单。人是设计工程师，偶发、移动、必须把型号写进 BOM。决策会分叉。一条从分类走进去，靠参数级联把候选收窄，最后拼出型号。另一条从工况走进去，先算出力和接口约束，再拿约束去对库。做完要带走的是型号、图、订货单，购物车只是顺手。

微信把现场换到了手机上。容器的规则我问过，那是后面才能开工的条件。真正让店这个比喻吃力的，是下一屏的公式。

---

## 查：型号是规则拼出来的

参数页里，模数咬着齿数，齿数咬着接口。每个产品有一组维度，维度之间有依赖：父项选了某个码，子项只放出允许的码。确认时要逐维检查，候选不合法就拦下。型号本身是一条模板，例如 `RG-M{module}-{precision}-{length}`、`R67-{ratio}-{mount}`，把选中的码填进花括号。没有模板时，就把有值的项用短横线接起来。

工程师在纸质样本上做的，是同一件事：按栏目往下勾，勾完读出订货代号。数字化之后，勾的过程变成级联，读代号的过程变成替换。语法换一套，模板还在。

确认的那一刻，记录里写入当时的参数包，以及拼好的型号。产品后来改名、下架、改规则，那一单仍是那一单。主数据会变，成交得留下自己的时间切片。MedRWA 里「金额对上了、来源却可能错」是规则写少了；这里把成交当时的选择钉死，怕的是规则以后变多、变少，历史单却跟着漂。

查这一路，计算很少。它吃的是样本结构和依赖表。电商目录也有筛选，差别在终点：这里的终点是可写入订货单的型号，不是一件可以随便换色的 SKU。

---

## 算：先出约束，再进库

齿条齿轮页不吃「再筛选一下」。水平还是垂直，载荷、速度、加速度填进去之后，力是算出来的：水平为 **μmg + ma**，垂直为 **mg + ma**，μ 缺省 0.1。再乘安全系数 1.5，得到必须扛住的力。转速和线速度还能反出节圆直径，力乘半径得到转矩。模数用 `√F / 18` 估一个下限。然后才进库：齿条或齿轮上带着许用载荷、模数、齿数；许用载荷够、模数不太小，才留下，再按安全系数排序。

电机配减速机是另一套分叉。先对接口：轴径、止口、轴伸，对不上直接丢掉。再对动力学：输出转矩要够，负载惯量与电机惯量之比，普通精度不超过 8，高精度不超过 3。接口是「装不装得上」，动力学是「转不转得动」。跨品牌电机库存在，是因为减速机这一侧要吃很多厂家的轴和惯量。

文件也按算和查分开。三视图是预渲染的图，看得见。STEP / CAD 按型号去已入库的文件里找，找不到就明确说这条型号还没有文件。订货单 PDF 用当时那条记录当场画。打包时把能找到的模型和二维图，加上订货单，塞进一个 ZIP。看得见的成本低，交得出去的真模型成本高，分层是故意的。

这一天的算法能跑，却还浅。齿条匹配会把产品表扫一遍；模数用根号力去估，不是从齿轮强度手册里逐步校核；哪些结果可以自动放行、哪些必须工程师再看一眼，我没有画完。工况算法、文件引擎、电机库、型号规则，四样里我摸到的是骨架：查靠模板和依赖，算靠公式再过滤，文件分预存和当场生成。更细的建模，这一天没有走完。

你对着一个长得像店的产品，也可以停在这一问：货架下面那个人，离开屏幕时带走的是一张订单，还是一组算过的约束？

## 话说完，工具才有东西可服从

作业和分叉一旦写下来，手会反复做同一件事：用母语写到另一双手可以按着施工。中午，文档和 ER 在桌上。下午，三端按文档铺开。骨架快，因为查、算、快照、文件分层已经被说完。语言在这里要写成规格。TypeScript 会不会，管的是谁敲键盘。

小程序、SaaS、包体积那三问，适合放在这一步附近：容器允许什么，规格才知道哪些交付必须留在云上。它们重要，只是不该再被叫做思维逻辑。

晚上两件事找上门时，我并没有一套现成的做法。真机打不开电脑上的地址，隧道递出去以后，接口地址和图片地址还得一起改。本地可以是 SQLite 或 MySQL，腾讯云个人免费版只给 PostgreSQL，整条线后来换成 PG。当时只想把眼前的卡住解开，于是去问 AI。选型作业没有重写。下一次同样的坑还能不能照用，我答不上来。摸着石头过河，算不上方法。开头写过，方法要在大量坚持里才现身。这一天只有一次。

连上和换库时摸到的几条，只是手边的痕迹：库在自己手里走直连，在云手里走云 API；云 API 不吃参数化绑定，就把占位符先转成字面量；两处地址一起改，接口通了图才不会裂。它们能让下一次少绊一跤，解释不了选销易为什么被做成这样。
