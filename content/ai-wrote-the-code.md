# 代码几乎 100% 是 AI 写的，我却打算把它放进简历

> 项目：[MedRWA Console](https://github.com/AMappama/med-rwa-demo) —— 医疗应收（医保/商保）收益权 RWA 运营台 Demo。
> 主链路：资产登记 → 审核 → 份额映射 → 认购 → 回款 → 对账 → 凭证 → 审计。

## 先交代一个真实的起点

做这个项目的过程中，我问过 AI 一个问题，原话留在我的学习记录里：

> 「npm 是做什么的？」

同一份记录里还有「Node.js 是做什么的？」「Mapper 在哪个文件夹？」。两天里我一共问了 39 个问题，后来让 AI 全部分级统计过：初级问题 24 个，占 61.5%。

这就是我的起点。我来自医疗行业，正在往「AI 辅助全栈」方向转，这条求职路我还没走通——项目做完了，工作还没拿到。所以这篇文章不是经验之谈，更谈不上方法论，只是想把这段经历如实记下来：一个不会写 Java 的人，用 AI 辅助做出了一个全栈 Demo，中间踩了什么、想了什么、留下了什么。

如果你也在类似的路上，也许有一两处能参考；如果你是有经验的工程师，也欢迎指出我理解错的地方。

## 一、开工前，我先想清楚这个项目要证明什么

它不是为了上线，是为了面试。那面试官需要看到什么？

我列的清单是：能把模糊目标拆成可测试的需求；能通过追问理解陌生业务，而不是复制代码；能发现 AI 遗漏的问题，并决定修、延后还是接受；能把一次经验沉淀成下次可用的东西。

同时把责任边界写死：**代码接近 100% 由 AI 生成**；我负责提目标、做选择、配环境、手动跑通流程。我不打算隐瞒这一点——整个做法的前提就是，「正确」得靠编译、接口响应、数据库状态这些外部证据说话，而不是 AI 的自我评价，也不是我的。

## 二、从一句话到一个能演示的系统

最初我只有一句：「做一个贴近目标公司业务的全栈 Demo。」

我没有直接让 AI 开写，而是先追问了几轮：目标公司的产品线在解决什么问题？哪条业务链适合做成能点击的后台？我的医疗背景能接上哪类资产？

收敛的结果是「医疗应收收益权 RWA」：医院有一笔以后医保/商保会打过来的钱，系统把这笔未来回款拆成可认购的份额，投资人买走，钱到账后核对入账。选它的原因很实际——有金额、有账期、有回款方，业务能闭环；我的行业经验用得上；而且比「病历上链」干净，患者隐私从一开始就排除在外。

同样重要的是「不做清单」：不上真链、不连真实医保和银行系统、不做完整会计总账。后来回看，这份清单挡住了好几次范围膨胀——包括 AI 的，也包括我自己的。

技术栈也是问出来的，不是背出来的。每个工具我只问三件事：解决什么问题、为什么选它、不选会怎样。Redis 就是这么被延后的——它不属于最小闭环。

然后按固定顺序拆解：角色 → 状态机 → 页面字段 → 数据库表 → 接口 → 最后才是代码。没有用一句「帮我写完整项目」开工。

## 三、AI 写的代码全部跑通了，但有两个地方账是错的

这部分是我觉得整段经历里最值得记录的，因为它回答了「代码都是 AI 写的，那你做了什么」。

### 金额对了，钱的来源是错的

AI 生成的对账逻辑很合理：核对金额，一致就允许「已匹配」。编译通过，页面能点，演示流畅——按很多教程的标准，项目已经完成了。

但我手动跑流程时停在一个地方：一笔**医保**资产，收到一笔**商保**公司打来的回款，金额恰好相同，系统判定匹配成功。

现实里这叫串账。这个漏洞测试抓不到，因为它不是代码错误，是**业务规则缺失**——「对」的定义本身写少了。后来补上第二重校验：医保资产必须对应医保对手方，不一致标记 `COUNTERPARTY_MISMATCH`，禁止放行。

说实话，能发现它靠的不是技术，是我原行业的习惯——来源核对、流程合规这些东西，在医疗里被训练了很多年。

### 一分钱的去向

另一个问题小到只有一分钱。回款按持仓份额分配，比例除不尽会有舍入尾差，AI 的实现是让最后一笔「吃尾差」保证账平。代码本身没毛病，这是常见工程手法。

但我复盘时越想越不对，记了一个 issue，里面是三个问题：尾差谁承担？合同有没有写？持仓排序稳不稳定——谁是「最后一笔」？在真实金融产品里，分配规则要写进认购协议、过法务的。

最后的决定是：**不改代码，标记 ACCEPTED_RISK，写明产品化前必须补合同约定。** 连「不修」也留了决策记录。这是我第一次意识到，判断哪些问题必须现在修、哪些可以带着走，这件事 AI 替不了——接受风险需要有人负责。

## 四、39 个问题，和我留下的东西

回到开头那份问题清单。我没有删掉暴露底子的部分，反而把 39 个问题全部归档：初级 24 个，中级 11 个，高级 4 个。

保留它一是诚实，二是它的时间轨迹本身有点意思：从「这个注解是什么」，到「请求为什么停住、403 从哪来」，再到最后问出「强制旧流水补银行回单号，会不会卡住历史回款、引发投诉」——这个问题已经不是技术问题了，它关心的是规则上线后伤不伤到存量数据。我不确定这算不算进步，但至少问题的层次在变。

项目收尾时，我把过程里真正起作用的约束整理成了一个六部分的 Prompt 骨架（目标、上下文、业务规则、范围、规范、验收标准——每一部分都对应过一次真实的跑偏），外加四份 SOP：需求拆解、AI 产物验证、全栈联调、Docker 排障。

做这些沉淀的动机很简单：这次的很多收获是碰出来的，我希望下次做类似的事，不用重新碰一遍。至于这套东西在下一个项目里灵不灵，我还没验证过，不敢打包票。

## 五、写在最后

这段经历目前只走到「作品集做出来了」这一步，后面的路——面试、追问、拿 offer——还没走。所以这篇文章没有资格给结论，只能给记录。

几句如实的自我评估：我现在能沿着「页面 → API → Controller → Service → Mapper」找到代码、下断点看数据流，但 Java 的很多基础概念还在建立中；我能发现业务层面的漏洞，但还写不了修复它的代码。这份作品集能证明的，大概是「我知道怎么和 AI 一起把一件事做到可验证」，仅此而已。

仓库在这里：[MedRWA Console](https://github.com/AMappama/med-rwa-demo)。`docker compose up --build` 可以直接跑，`docs/` 目录下有完整的案例文档、SOP、issue 记录，还有那份 39 个问题的统计——包括「npm 是做什么的」那条，我没删。

如果你看完有任何想法，不管是指出问题还是聊聊类似的经历，都欢迎。
